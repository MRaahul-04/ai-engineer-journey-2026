Day 11 — ROC Curve & AUC

Week 2 · Day 11 of 84 · AI Engineer Journey 2026

The one-line idea

Day 10 sliced one borderline student's threshold from 0.5 to 0.3 and watched Precision/Recall trade against each other — a single before/after snapshot. Today: sweep the threshold across every possible value, plot the resulting curve, and compress the whole tradeoff into one number (AUC).

TPR — same formula as Recall, new name

TPR = TP / (TP + FN)
Identical to Day 10's Recall. Row-based: only looks at the actual-YES row — "of all real positives, how many did I catch?"

FPR — Recall's mirror on the negative side

FPR = FP / (FP + TN)
Also row-based, but on the actual-NO row — "of all real negatives, how many did I wrongly flag as positive?"

TPR uses the left column's row-total (TP+FN). FPR uses the right column's row-total (FP+TN). Neither touches Precision's column-based view at all.

Why TPR and FPR move together

Raising the threshold can only shrink the "Predicted: YES" group — anyone who clears a higher bar would also clear a lower one, never the reverse. Both TP and FP live inside that same shrinking group. Meanwhile TP+FN and FP+TN are both fixed dataset totals (they don't depend on threshold at all). So as threshold rises: TP can only shrink → TPR falls. FP can only shrink → FPR falls. Same mechanism, both metrics move in the same direction.

The two extremes — proven by hand

threshold = 1.0 (impossibly strict, nobody predicted YES)
  TP=0, FP=0, FN=4, TN=6  ->  TPR=0, FPR=0   <- point (0,0)

threshold = 0.0 (no filter, everybody predicted YES)
  TP=4, FP=6, FN=0, TN=0  ->  TPR=1, FPR=1   <- point (1,1)
Every real threshold in between produces a point somewhere along the path from (0,0) to (1,1). Connecting all of them, swept continuously, traces the ROC curve.

Reading the plot

  • Diagonal line (FPR=TPR always) = random guessing, zero information. Covers exactly half the unit square → area = 0.5.
  • Bulging toward top-left = catching real positives before being forced into false alarms → better model.
  • Hugging the top-left corner (straight up the left edge, then flat across the top) = the perfect-classifier path → covers the entire unit square → area = 1.0.
  • Below the diagonal = worse than random — usually a sign something is inverted.

AUC — area under the curve

AUC = 0.5   ->  no better than a coin flip
AUC = 1.0   ->  perfect separation at some threshold
AUC < 0.5   ->  worse than random (likely inverted labels/predictions)
Intuitive meaning: AUC is the probability that the model ranks a randomly chosen true positive higher than a randomly chosen true negative — a statement about ranking quality, not about any single threshold's accuracy.

Building it from scratch

def compute_roc_point(y_actual, probs, threshold):
    predicted = (probs >= threshold).astype(int)
    TP = np.sum((predicted == 1) & (y_actual == 1))
    FP = np.sum((predicted == 1) & (y_actual == 0))
    FN = np.sum((predicted == 0) & (y_actual == 1))
    TN = np.sum((predicted == 0) & (y_actual == 0))
    TPR = TP / (TP + FN)
    FPR = FP / (FP + TN)
    return FPR, TPR

thresholds = np.linspace(0, 1, 21)
roc_points = [compute_roc_point(y_actual, probs, t) for t in thresholds]
Swept 21 thresholds across a near-perfectly-separable 1-feature dataset. TPR hit 1.0 immediately and stayed there while FPR was still climbing from 0 — the visual signature of a strong classifier.

The sorting bug — real debugging, not just theory

First attempt sorted points by FPR alone before integrating with np.trapezoid: 
order = np.argsort(fprs)   # BUG: unstable when FPR has ties
Result: AUC = 0.9286 instead of the true value. Many thresholds tied at FPR=0.000, and sorting by FPR alone left their TPR values in arbitrary order — the trapezoid rule then zig-zagged between out-of-order points instead of tracing the real (monotonic) curve, silently losing area.
Fix: sort by threshold instead (guaranteed no ties, since every threshold in the sweep is unique) — this naturally preserves the correct monotonic TPR order within every FPR tie group. 
order = np.argsort(thresholds)[::-1]
fprs_sorted = np.array(fprs)[order]
tprs_sorted = np.array(tprs)[order]
auc_fixed = np.trapezoid(tprs_sorted, fprs_sorted)   # -> 1.0000, matches sklearn exactly
Lesson: never sort multi-column data by a column that can have duplicates unless you add a tiebreaker — sort by the unique column instead.

NumPy 2.0 gotcha

np.trapz was removed in NumPy 2.0, renamed to np.trapezoid. A reminder that library APIs shift between when material is written and when it's actually run — always check the error message rather than assuming the code itself is wrong.

Verified against sklearn

from sklearn.metrics import roc_curve, roc_auc_score
fpr_sk, tpr_sk, thresholds_sk = roc_curve(y_actual, probs)
auc_sk = roc_auc_score(y_actual, probs)
sklearn only generates points at the actual unique probability values (not an arbitrary evenly-spaced grid) — far fewer points (4 vs our 21), but exact at every real transition. Final result after the sorting fix: 
Scratch AUC (fixed):  1.0000
sklearn AUC:           1.0000   ✓ exact match

Interview questions — plain-language answers

Q1. What's the difference between Recall and TPR?
Nothing — identical formula, TP/(TP+FN). Recall is the name used in Precision/Recall context; TPR is the name used in ROC/AUC context.
Q2. Why does FPR use FP/(FP+TN) instead of FP/(FP+TP)?
FPR is row-based like Recall/TPR — it only looks at people who are actually negative (the FP+TN row): "of all real NOs, how many did I wrongly flag?" FP/(FP+TP) would be a column-based view, which isn't what FPR measures.
Q3. Why do TPR and FPR always move in the same direction as threshold changes?
Both TP and FP live in the same "Predicted: YES" group, which can only shrink as threshold rises. Since TP+FN and FP+TN are both fixed dataset totals, shrinking TP shrinks TPR and shrinking FP shrinks FPR — same underlying lever.
Q4. What does AUC actually mean, intuitively?
The probability the model ranks a randomly chosen true positive higher than a randomly chosen true negative. 0.5 = coin flip, 1.0 = always ranks correctly.
Q5. Why did the from-scratch AUC break at first, and what's the real lesson?
np.argsort() on one column doesn't handle ties safely — sorting by FPR alone scrambled TPR order within tie groups, corrupting the trapezoidal area. Fix: sort by a column guaranteed unique (threshold) instead. Lesson: never sort multi-column data by a column with possible duplicates unless a tiebreaker is added.
