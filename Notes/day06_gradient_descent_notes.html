Day 6 — Gradient Descent

Week 1 · Day 6 of 84 · AI Engineer Journey 2026

The one-line idea

Day 5 solved for the exact best weights in one shot using (XᵀX)⁻¹. Today's question: what happens when the dataset has thousands or millions of features? The exact formula stops being usable — so instead of solving in one shot, we start with a guess and walk downhill, a little at a time, until we arrive at (or near) the same answer.

Why the exact formula breaks at scale — measured, not assumed

Timed np.linalg.inv() on real matrices: 
n=     2 -> 0.002 sec
n=   100 -> 0.023 sec
n=  1000 -> 0.340 sec
n=  5000 -> 3.233 sec
n= 10000 -> 23.779 sec
Doubling matrix size (5000→10000) made it ~7x slower, not 2x — matrix inversion is roughly O(n³) — cubic, not linear. At millions of features (real embedding models), this becomes completely impossible, even once.

Why cubic: think Gaussian elimination — roughly n rows × n columns × n operations-per-cancellation. Vectorization makes each of those operations fast, but it can't reduce how many there are.

SSE is a U-shaped bowl

Plotting SSE against different guesses of w (one feature, no bias) on a tiny dataset produced a clean U-shape — SSE is high far from the true minimum, and dips to a single lowest point: 
w=-1.0 -> SSE=273.00
w= 0.0 -> SSE= 86.00
w= 1.0 -> SSE=  9.00   <- near the minimum
w= 2.0 -> SSE= 42.00
w= 3.0 -> SSE=185.00
This U-shape is guaranteed by the math (same reason XᵀX "opens upward" from Day 5) — SSE being built from squared terms means it can never have more than one minimum for linear regression.

Gradient = slope; descent = subtract

On the left side of the bowl, slope (gradient) is negative → need to increase w. On the right side, gradient is positive → need to decrease w. In both cases: 
w_new = w − (learning_rate × gradient)
Always subtract, never add — subtracting a negative gradient correctly increases w; subtracting a positive gradient correctly decreases it. Verified: at w=0, gradient=-132, learning_rate=0.01 → w_new = 0 − (0.01 × -132) = 1.32.

The single-feature gradient formula

gradient = -2 * sum(x * (y - predicted))
Generalizes directly to the full-matrix version from Day 5's derivation (dSSE/dw = -2XᵀXw + 2Xᵀy = -2Xᵀ(y-Xw)) — same formula, matrix notation just lets it scale to any number of features at once, same pattern as @ scaling dot_product_scratch on Day 3.

Watching convergence happen, step by step

step 0: w=0.0000  gradient=-132.00  SSE=86.00
step 1: w=1.3200  gradient=-132.00  SSE= 7.59
step 2: w=1.1880  gradient=  13.20  SSE= 6.81
step 3: w=1.2012  gradient=  -1.32  SSE= 6.80
step 5: w=1.2000  gradient=  -0.01  SSE= 6.80   <- converged
Gradient magnitude shrinks on its own as we approach the minimum — no manual slowdown needed. This falls directly out of the bowl's shape: steep far away, flat near the bottom. Big confident steps far out, tiny cautious steps near the answer — for free.

Learning rate — the real danger zone

Too small (0.001): converges, but slowly — wastes compute.

Too large: doesn't just slow down — diverges completely. Tested learning_rate=0.5 starting at w=0: SSE exploded from 86 → 230,954 → 673 million → ...→ 4×10²⁹ by step 8. Overshoots the minimum onto a steeper part of the bowl, producing an even bigger gradient next step — snowballs out of control.

On the scaled student dataset, the real boundary was sharp: 
lr=0.001 -> converged (SSE=7.17)
lr=0.01  -> converged (SSE=4.26)
lr=0.1   -> DIVERGED (SSE=inf)
lr=0.5, 1.0, 2.0 -> DIVERGED (SSE=nan)

GradientDescentScratch — the class

class GradientDescentScratch:
    def __init__(self, learning_rate=0.01, n_iterations=1000):
        self.learning_rate = learning_rate
        self.n_iterations = n_iterations
        self.loss_history = []          # empty list, nothing recorded yet

    def fit(self, X, y):
        ones = np.ones((X.shape[0], 1))
        X_b = np.hstack([ones, X])       # bias trick, same as Day 5
        self.w = np.zeros(X_b.shape[1])  # start anywhere on the bowl

        for i in range(self.n_iterations):
            predictions = X_b @ self.w
            gradient = -2 * X_b.T @ (y - predictions)
            self.w = self.w - self.learning_rate * gradient

            sse = np.sum((y - predictions) ** 2)
            self.loss_history.append(sse)   # track progress each step
        return self

    def predict(self, X):
        ones = np.ones((X.shape[0], 1))
        X_b = np.hstack([ones, X])
        return X_b @ self.w
Verified against sklearn on the student dataset (scaled features): [67.5714, 9.7273, 1.2643, 1.8174] — identical on both, to 4 decimals.

Feature scaling — Gradient Descent's real requirement

Same learning rate (0.05), only difference = scaling: 
Scaled features   -> weights match sklearn exactly
Unscaled features -> weights = [nan, nan, nan, nan]  (total blowup)
The Normal Equation (Day 5) doesn't care about feature scale. Gradient Descent does. Uneven feature ranges create a "canyon" — steep in one direction, flat in another — and a single learning rate that's safe for one dimension can explode another. This is the real, practical reason feature scaling is standard preprocessing before gradient-based training.

Diminishing returns on iteration count

n_iterations=    10 -> SSE=479.238997
n_iterations=   100 -> SSE=  4.372114   <- most progress happens here
n_iterations=  1000 -> SSE=  3.818182
n_iterations= 10000 -> SSE=  3.818182   <- identical to 6 decimals, wasted compute
10x more iterations (1000→10000) bought essentially nothing. This is the real-world motivation for early stopping — monitor loss_history, stop once improvement drops below a tiny threshold, instead of committing to a fixed iteration count blindly.
